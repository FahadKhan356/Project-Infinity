Aktivacity Central Project Portal1. Project OverviewThe Aktivacity Portal will be a centralized internal platform connecting all departments involved in project delivery.The main purpose of the portal is to manage the complete lifecycle of a project:Sales ? Project Creation ? Project Manager ? Team Lead ? Executive ? Production ? QA ? Delivery ? Client Revision ? Final DeliveryThe system should allow different departments to see and manage only the information relevant to their role while management has broader visibility.Departments• Sales.• Project Management.• Video.• Design.• Development.• Social Media.• SEO.• Management / Admin.2. User RolesThe initial system should have the following user roles:Management• CEO.• COO.Management should have visibility across projects, pricing, teams, progress and deliveries.SalesSales representatives create projects/orders, enter client/project information, pricing and requirements, receive approved deliveries and manually deliver them to clients.Project ManagerProject Managers oversee projects from start to completion.They assign projects to Team Leads, manage overall planning, monitor progress and perform QA where required.Team LeadEach Team Lead manages executives/members belonging to their department.They plan work, assign tasks, monitor deliverables and perform QA.ExecutiveExecutives are individual team members who receive assigned work, work on projects and upload deliverables.3. Sales PortalProject CreationWhenever a new project is confirmed, Sales will manually create the project in the portal.Sales should be able to enter:• Client name.• Project name.• Project objective.• Project description.• Project/order type.• Department/team required.• PO / project requirements.• Client notes.• Internal notes.• Number of deliverables.• Deadline.• Attachments.• Pricing.• Other relevant project information.Pricing VisibilityPricing must be restricted.Pricing should only be visible to:• CEO.• COO.• Authorized Management.• Project Manager.• Sales.Team Leads and Executives should NOT see project pricing.4. Project Creation FlowOnce Sales creates the project:Sales creates project ? Project enters Project Manager’s portal ? Project Manager reviews project ? Project Manager assigns project to relevant Team LeadThe project should automatically appear in a dedicated section for Project Managers called:Project Closure ReportThis section should show newly created projects requiring project-management action.5. Project Manager PortalThe Project Manager is responsible for managing the overall project.Main Sections• Dashboard.• Project Closure Report.• Planning.• Projects.• QA.• Revisions.• Deliveries.• Team Overview.• Reports.Project Closure ReportThis is where newly created projects from Sales appear.The Project Manager can:• Open project.• Read project objective.• Read PO.• Review requirements.• Review notes.• Review deadline.• See deliverables.• See pricing.• Assign project to a Team Lead.• Add internal notes.• Set priority.• Set project deadline.Once assigned, the project moves into the relevant team’s workflow.6. Planning SystemThere should be two levels of planning:Project Manager PlanningThe Project Manager should have an overall planning page.The PM can see:• All teams.• All Team Leads.• All team members.• Projects assigned.• Current workload.• Start dates.• End dates.• Deliverables.• Project status.The PM should have visibility across all departments.Team Lead PlanningEach Team Lead should have their own planning page.The Team Lead will only see:• Their team.• Their team members.• Projects assigned to their team.• Current workload.• Planned projects.• Deadlines.• Deliverables.7. Assigning WorkFrom the Planning page, a Team Lead can assign work to a specific Executive.Assignment should include:• Project.• Executive/member.• Start date.• End date.• Number of deliverables.• Deliverable description.• Comments/instructions.• Attachments/references.• Priority.Example:Project: Client ABC Social Media VideosExecutive: AhmedStart: 24 SeptemberEnd: 26 SeptemberDeliverables: 2Progress: 0/2When the executive uploads the first deliverable:1/2After the second:2/2The system should automatically update the progress.8. Executive PortalWhen an Executive logs in, the primary page should be their:ProjectsThere should be two major sections:Current ProjectsProjects currently assigned/planned to the Executive.Each project should display:• Project name.• Client/project identifier.• Start date.• End date.• Deadline.• Deliverables.• Progress.• Priority.• Instructions.• Comments.• Revision status.Ongoing / Previous ProjectsA history of projects previously assigned to that Executive.They should be able to open completed/previous projects for reference.9. Executive Project ViewWhen an Executive opens a project, they should be able to see:• Project objective.• PO.• Project requirements.• Notes.• Instructions.• Assigned deliverables.• Deadline.• Other team members assigned to the project.• Files uploaded by other team members.• Revisions.• Comments.The Executive can:• Upload files.• Add comments.• View other team members’ files.• View project revisions.• Respond to revision requirements.10. Shared Project WorkspaceMultiple Executives can be assigned to the same project.All assigned members should be able to access the same project workspace.For example:Project ABC• Video Executive ? uploads video.• Design Executive ? uploads thumbnails.• SEO Executive ? uploads SEO content.• Social Media Executive ? uploads social media assets.Each assigned member can see the relevant files uploaded to the shared project.The system should maintain:• File name.• Uploaded by.• Upload date/time.• Version.• Comments.• Status.11. Deliverable ProgressEvery assigned task should have a deliverable counter.Example:Deliverables: 0/3After first upload:1/3After second:2/3After third:3/3The system should automatically update this based on uploaded/accepted deliverables.12. Team Lead QA PanelEvery Team Lead should have a dedicated:QA PanelWhenever an Executive uploads a deliverable, it should appear in the Team Lead’s QA panel.Example:Project ABCExecutive: AhmedDeliverable: Video 01Status: Awaiting QAThe Team Lead can:• Open file.• Review file.• Approve.• Reject.• Request changes.• Add QA comments.• Forward approved file.13. Project Manager QAThe Project Manager should also have a QA panel.The PM can see deliverables that require PM-level review.Depending on the project workflow, the file can go through:Executive ? Team Lead QA ? Project Manager QA ? Sales DeliveryOR, if PM review is not required:Executive ? Team Lead QA ? Sales DeliveryThe exact QA requirement should be configurable per project.14. Sales Delivery PanelOnce a deliverable has passed the required QA process, it should appear in:Sales ? DeliveriesSales should see:• Project.• Client.• Deliverable.• File.• Version.• QA status.• Date approved.• Comments.• Delivery status.Sales will manually deliver the approved file to the client.The portal does NOT need to automatically send the file to the client in the first version.Sales can mark the file as:• Pending Delivery.• Delivered.• Client Feedback Received.• Revision Required.• Completed.15. Revision SystemSales should have the ability to create a revision whenever feedback is received from a client.Creating a RevisionSales can select:Project ? Add RevisionAnd enter:• Revision title.• Client feedback.• Revision details.• Relevant deliverable.• Priority.• Deadline.• Attachments/reference files.• Comments.Example:Revision #03Client feedback:“Please change the opening scene and update the logo placement.”16. Revision VisibilityOnce Sales creates a revision, it should automatically appear for the relevant teams.Project ManagerCan see revisions across all projects.Team LeadCan see revisions related to their team.ExecutiveCan see revisions related to projects currently assigned to them.Example:Video Team Lead? sees video-related revisions.Design Team Lead? sees design-related revisions.Video Executive? sees revisions assigned/relevant to their projects.17. Revision WorkflowRecommended flow:Sales creates revision?Project Manager receives revision?Relevant Team Lead receives revision?Team Lead assigns revision to Executive?Executive works on revision?Executive uploads revised file?Team Lead QA?Project Manager QA if required?Sales receives revised deliverable?Sales delivers to client18. Project StatusEvery project should have a clear status.Suggested statuses:• New.• Awaiting Assignment.• Planned.• In Progress.• QA.• Revision Required.• Approved.• Ready for Delivery.• Delivered.• Completed.• On Hold.• Cancelled.19. File VersioningFiles should not simply overwrite each other.Example:Video_Final_v1Video_Final_v2Video_Final_v3The system should maintain:• Version number.• Uploaded by.• Date/time.• Previous versions.• Comments.• QA status.This is particularly important for revisions.20. NotificationsThe system should generate internal notifications when an important action occurs.Examples:Sales• Project created.• Project approved by PM.• Deliverable ready for delivery.• Revision received.• QA rejected.Project Manager• New project created.• Team Lead assigned.• Deliverable uploaded.• QA required.• Revision created.• Project delayed.Team Lead• New project assigned.• New task assigned.• Executive uploaded file.• QA required.• Revision received.• Deadline approaching.Executive• New project assigned.• New task assigned.• Revision received.• QA approved.• QA rejected.• Deadline approaching.21. DashboardEach role should have a different dashboard.Management DashboardManagement should have high-level visibility:• Total active projects.• Projects completed.• Projects in production.• Projects in QA.• Projects awaiting delivery.• Projects in revision.• Team workload.• Project delays.• Sales/project value.• Department performance.Pricing/revenue information should only be visible to authorized users.Project Manager Dashboard• New projects.• Active projects.• Projects by department.• Projects in QA.• Pending revisions.• Delayed projects.• Upcoming deadlines.• Team workload.Team Lead Dashboard• Team projects.• Pending assignments.• Active tasks.• QA queue.• Revisions.• Upcoming deadlines.• Team workload.Executive Dashboard• Today’s assignments.• Current projects.• Pending deliverables.• Completed deliverables.• Revisions.• Upcoming deadlines.22. Search & FiltersThe portal should have global search and filtering.Users should be able to search by:• Project name.• Client.• Project ID.• Team.• Team Lead.• Executive.• Status.• Date.• Revision.• Delivery status.Permissions should still apply to search results.For example, an Executive should not be able to search and discover projects they don’t have access to.23. PermissionsPermissions are extremely important.CEO / COOFull access.SalesAccess to:• Projects they create/are authorized to view.• Project information.• Pricing.• Client information.• Deliveries.• Revisions.• Delivery status.Project ManagerAccess to:• All assigned projects.• Project pricing.• All relevant teams.• Planning.• QA.• Revisions.• Deliveries.• Reports.Team LeadAccess to:• Their department/team.• Assigned projects.• Planning.• Their team members.• QA.• Relevant revisions.No pricing visibility unless specifically authorized.ExecutiveAccess only to:• Projects assigned to them.• Shared project workspace for projects they are part of.• Their assignments.• Their deliverables.• Relevant revisions.• Their own project history.No project pricing.24. Project IDEvery project should automatically receive a unique Project ID.Example:AKT-2026-0001This ID should be used throughout the system for:• Project tracking.• Files.• Revisions.• QA.• Delivery.• Reporting.25. Activity / Audit LogEvery important action should be recorded.Example:24 Sep, 10:32 AM — Sales created project24 Sep, 11:05 AM — PM assigned project to Video Team24 Sep, 11:30 AM — Team Lead assigned task to Ahmed25 Sep, 4:20 PM — Ahmed uploaded Video V125 Sep, 5:10 PM — Team Lead rejected Video V126 Sep, 2:30 PM — Ahmed uploaded Video V226 Sep, 3:00 PM — Team Lead approved Video V226 Sep, 3:30 PM — PM approved26 Sep, 4:00 PM — Sales received deliveryThis will help management track accountability and project history.26. Basic Overall WorkflowThe complete system should work approximately like this:1. SALESCreate project?Add objective, PO, requirements, deliverables, deadline and pricing2. PROJECT MANAGERProject appears in Project Closure Report?PM reviews project?PM assigns relevant Team Lead3. TEAM LEADProject appears in Team Lead planning?Team Lead selects Executive(s)?Assigns start date, end date, deliverables and instructions4. EXECUTIVEProject appears under Current Projects?Executive opens project?Reads PO/instructions?Works on deliverable?Uploads file5. QAFile appears in Team Lead QA?Team Lead approves/rejectsIf rejected ? Executive receives feedback and uploads new version.If approved ? PM QA if required.6. SALESApproved file appears in Sales Deliveries?Sales manually delivers to client7. CLIENT REVISIONSales receives client feedback?Sales creates Revision?Revision appears for PM/Team Lead/Executive?Executive works on revision?QA?Sales receives revised file?Sales delivers to client8. COMPLETIONAll deliverables completed?Project marked Completed?Project remains available in historical/ongoing project records.27. Important Development PrincipleThe portal should be built around a single Project record.Every project should contain and connect:• Client.• Sales owner.• Project Manager.• Team Lead.• Executives.• Objective.• PO.• Requirements.• Pricing.• Tasks.• Deliverables.• Files.• QA.• Revisions.• Comments.• Deadlines.• Delivery history.• Activity log.This prevents departments from creating duplicate versions of the same project.The same Project ID should follow the project throughout its entire lifecycle.28. Phase 1 / MVPFor the first version, focus on the core workflow:Authentication & Roles• Login.• Role-based access.• User management.Sales• Create project.• Add PO/details.• Add pricing.• View projects.• Add revisions.• View deliveries.Project Manager• Project Closure Report.• Assign Team Leads.• Overall planning.• QA.• Revisions.• Project tracking.Team Lead• Team planning.• Assign executives.• Set deadlines.• Set deliverables.• QA.• Revisions.Executive• Current Projects.• Previous Projects.• Project details.• File upload.• Shared project workspace.• Revisions.System• Notifications.• File management.• Versioning.• Project statuses.• Activity logs.• Search/filtering.29. Future FeaturesThese do not need to be included in the first version but the architecture should allow them later:• Automated client portal.• Client login.• Client approval/rejection.• Automatic email notifications.• Slack integration.• WhatsApp notifications.• Time tracking.• Employee productivity reports.• Team performance analytics.• Profitability reports.• Automated invoices.• CRM integration.• Sales pipeline.• Recurring projects.• AI project summaries.• AI task assignment.• AI deadline prediction.• Automated client delivery.• Cloud storage integrations.• Mobile application.30. Main ObjectiveThe portal should become Aktivacity’s central operating system for project delivery.The goal is that once Sales creates a project, the entire organization can follow that project inside one system without relying on scattered WhatsApp messages, Slack conversations, spreadsheets or manual tracking.Every project should have a clear:Owner ? Team ? Assignment ? Deadline ? Deliverable ? QA ? Revision ? Delivery ? Completionwith complete visibility and accountability at every stage.Additional Requirements31. Client History & Repeat ClientsThe system should maintain a permanent Client Profile separate from individual projects.A client may have one project or hundreds of projects over multiple months.The Client Profile should contain:• Client name.• Company name.• Contact information.• Sales representative.• Client notes.• Services being provided.• Client status.• Date client started.• Client type.• Previous projects.• Current projects.• Monthly history.The purpose is to make the client a permanent record rather than creating a completely new client every time Sales creates a project.32. Monthly Project StructureFor long-term/retainer clients, every month’s work should be organized separately.Example:ClientABC Company2026• January 2026.• February 2026.• March 2026.• April 2026.• May 2026.• June 2026.• July 2026.• August 2026.• September 2026.Each month can contain multiple projects/orders.For example:ABC Company ? September 2026• 10 Social Media Videos.• 20 Social Media Designs.• SEO Monthly Work.• Website Updates.• 4 Blog Articles.Each of these can be individual projects while still belonging to the same client and month.33. Previous Month HistoryEveryone with the appropriate permissions should be able to access previous months.For example:ABC CompanyCurrent Month:September 2026Previous Months:• August 2026.• July 2026.• June 2026.• May 2026.• April 2026.When someone opens August 2026, they should be able to see what was delivered during that month.This should include:• Projects.• Deliverables.• Files.• Final approved files.• Revisions.• Comments.• Team members involved.• Delivery dates.• Project status.This is particularly important for recurring clients because the team may need to look at previous work before starting the next month’s work.34. Client ? Month ? Project ? Deliverables StructureThe recommended hierarchy is:CLIENT?MONTH?PROJECT / ORDER?TASKS / ASSIGNMENTS?DELIVERABLES?FILES / VERSIONSThis should be the core structure of the system.Example:Client: ABC Company? September 2026? Project: Social Media Content? Task: Video Editing? Executive: Ahmed? Deliverables: 5? Files:• Video 01 V1.• Video 01 V2.• Video 02 V1.• Video 03 V1.• etc..35. Client Overview PageWhen opening a Client Profile, users with permission should see a complete overview.Example:ABC CompanyCurrent MonthSeptember 2026Active Projects5Completed Projects42Total Months18Current MonthProjectTeamStatusProgressSocial VideosVideoIn Progress6/10Social DesignsDesignQA18/20SEOSEOIn Progress70%There should also be a View Previous Months option.36. Monthly ArchiveCompleted months should automatically become part of the client’s historical archive.For example:ABC CompanySeptember 2026CurrentAugust 2026CompletedJuly 2026CompletedJune 2026CompletedOpening a month should show the complete activity and deliverables for that period.The archive should be read-only for most users after the month is closed, while authorized users can still reopen/edit records if necessary.37. New Month CreationFor recurring clients, Sales should have a simple option:Create New MonthExample:Client:ABC CompanyCurrent month:September 2026Sales clicks:+ Create October 2026The system creates the new monthly workspace while carrying forward the permanent client information.Client information should NOT need to be entered again.38. Copy Previous MonthFor long-term clients, it would be useful to have:Copy Previous MonthExample:September 2026 contained:• 10 Videos.• 20 Designs.• SEO.• 4 Blogs.Sales can select:Copy August ? SeptemberThe system copies the project structure/order requirements but should allow Sales to modify:• Deliverable quantities.• Deadlines.• Requirements.• Pricing.• Notes.• New projects.• Removed projects.Important:Files and completed deliverables should NOT automatically be copied as new deliverables.Only the project/order structure should be copied.39. Monthly ReportingThe system should eventually provide monthly client reports.Example:ABC Company — September 2026Projects:8Deliverables:47Completed:42In Revision:3Pending:2Departments involved:• Video.• Design.• SEO.• Social Media.This can later be used by Sales and Management to understand the work delivered to each client.40. Local Server ArchitectureThe entire portal should be designed to operate on Aktivacity’s local/internal server.The initial system does NOT need to depend on cloud hosting for normal operation.The portal should be accessible through the company’s internal network.Example:http://aktivacity-server/orhttp://192.168.x.x/depending on the final network configuration.Employees connected to the Aktivacity network should be able to access the portal through their browser.41. Browser-Based Local ApplicationThe portal should be a web application rather than software that needs to be installed individually on every employee computer.Employees should simply open a browser and access the internal portal.For example:Chrome / Edge / Safari? Aktivacity Portal? Login? User sees their appropriate dashboard.This makes deployment and updates much easier.42. Local File StorageProject files should initially be stored on Aktivacity’s local server.For example:Aktivacity Server? Projects? Clients? ABC Company? 2026? September? Project 001? Deliverables? Video? V1 / V2 / FinalThe exact physical folder structure should be decided by the developer, but the application should maintain a logical structure around:Client ? Month ? Project ? Deliverable ? Version43. File Access PermissionsEven though files are stored locally, users should NOT have unrestricted access to the server’s file system.Employees should access project files through the portal.The portal should control:• Who can view files.• Who can upload files.• Who can delete files.• Who can download files.• Who can approve files.For example:An Executive should not be able to browse the server and access another department’s files simply by opening a network folder.44. Local Server BackupBecause the system will be hosted locally, backups are extremely important.The developer should implement an automated backup system.At minimum:Database BackupRegular automated backups of:• Users.• Clients.• Projects.• Tasks.• Revisions.• QA records.• Comments.• Activity logs.• Other database information.File BackupRegular backups of uploaded project files.The backup destination should ideally be separate from the primary server.For example:Primary Server?Secondary Backup Server / NAS / External Backup StorageThe exact backup method can be finalized during technical planning.45. Server Failure ConsiderationThe developer should design the system so that a failure of the main server does not result in permanent loss of project information.The developer should document:• Backup frequency.• Backup location.• Database restoration procedure.• File restoration procedure.• Server recovery procedure.46. Internet DependencyThe core portal should work without requiring an external internet connection.Internal functionality such as:• Creating projects.• Assigning tasks.• Uploading files.• QA.• Comments.• Revisions.• Viewing client history.• Viewing previous months.• Project tracking.should work entirely within the local network.Internet access may be required later for optional integrations such as:• Email.• WhatsApp.• Slack.• External cloud storage.• Client portal.• AI services.Those should be treated as optional integrations rather than dependencies of the core system.47. Important Architecture RequirementThe developer should NOT build the system around individual monthly projects alone.The database should have a permanent relationship between:Client? Client Months? Projects? Tasks? Assignments? Deliverables? Files? QA? Revisions? DeliveryThis is important because a client may remain with Aktivacity for several years.Example:Client: ABC Company2026:• January.• February.• March.• April.• ....• December.2027:• January.• February.• ....The entire history should remain connected to the same client profile.48. Long-Term ObjectiveThe portal should eventually become Aktivacity’s internal central production operating system.A user should be able to search:ABC Companyand immediately understand:• What are we doing for this client currently?.• What did we deliver last month?.• What did we deliver six months ago?.• Which teams are working on them?.• Which projects are active?.• Which deliverables are pending?.• What revisions are open?.• What files were finally delivered?.• Who worked on the project?.• What was the project history?.All of this should be available from one centralized client/project record.
